# Cache — ce qu'il faut faire (et ne pas faire) sur dmoptiquesarl.com

> **23/10/2026.** Écrit pour répondre à une demande précise de King : « écris la Cache Rule exacte,
> puis dis-moi où la coller ». La réponse honnête est en deux temps : **la règle du tableau de bord
> ne réglera rien sur cet hébergement-ci**, et **le correctif est déjà dans le dépôt**. Les deux sont
> détaillés ci-dessous, avec la source de chaque affirmation.

---

## 1 · Le constat mesuré

Le portique `tools/qa/audit_delivery.py` relève **494 images et 7 polices** servies avec
`Cache-Control: public, max-age=0, must-revalidate`. Concrètement : à chaque visite, le navigateur du
patient redemande au réseau **chaque photo de monture** avant de l'afficher. Sur un téléphone à Douala,
c'est la différence entre une page qui s'ouvre et une page qu'on quitte.

Ce n'est pas un réglage oublié de King : c'est **le défaut de Cloudflare Workers static assets**, écrit
noir sur blanc dans la doc — *« Cache-Control: public, max-age=0, must-revalidate — Sent when the
request does not have an Authorization or Range header »*
(<https://developers.cloudflare.com/workers/static-assets/headers/>).

---

## 2 · Pourquoi une Cache Rule ne corrigerait pas ça ici

DM OPTIQUE n'est pas servi par Cloudflare **Pages** ni par un serveur d'origine derrière la zone : il
est servi par un **Worker** (`wrangler.toml` → `[assets]`, Worker `dmoptiquesarl`, publié depuis le
22/10). Or la doc Cloudflare est explicite : *« No zone configuration for caching applies to Workers
Caching. Cache Rules, Cache Response Rules, Page Rules, cache level settings, the zone's default
cached-file-extensions list, and every other zone-level cache control have no effect on a Worker's
cache »* (<https://developers.cloudflare.com/workers/cache/>).

La question a déjà été posée par d'autres : *« when a workers project has a static assets binding,
these assets are served by bypassing the cloudflare worker. Using any sort of CF configuration such as
cache rules or page rules also does not work »*
(<https://community.cloudflare.com/t/workers-static-assets-cache-control/872403>).

**Conséquence pratique** : coller une Cache Rule dans le tableau de bord donnerait l'impression du
travail fait, sans un octet de cache en plus. C'est exactement l'erreur du `/*.webp` du 23/10 au matin
— un motif qui a l'air juste et qui ne matche rien. On ne la refait pas.

---

## 3 · Le correctif réellement livré : `_headers` dans le dépôt

Workers lit un fichier `_headers` posé **dans le dossier publié** et applique ses règles aux assets :

> *« The default response headers served on static asset responses can be overridden, removed, or
> added to, by creating a plain text file called `_headers` … in the static asset directory of your
> project. »* — <https://developers.cloudflare.com/workers/static-assets/headers/>

C'est ce que fait `hosting/previews/dmoptic/_headers`, mis à jour aujourd'hui :

| Chemin | `Cache-Control` | Pourquoi |
|---|---|---|
| `/fonts/*` | `public, max-age=31536000, immutable` | polices, contenu stable |
| `/montures/*` | `public, max-age=604800` | photos de montures — 7 jours |
| fichiers racine `.webp` / `.png` / `.ico` / `.jpg` (11 blocs explicites) | `public, max-age=31536000, immutable` pour `dm-logo`, `cabinet-hero*` ; 7 jours pour le reste | ces fichiers sont à la racine : un motif par dossier ne les couvre pas |
| HTML | **rien** — on laisse le défaut `max-age=0, must-revalidate` | une page corrigée doit s'afficher tout de suite |

Pourquoi onze blocs explicites au lieu de `/*.webp` : la doc Pages n'accepte le splat qu'en fin de
motif, la doc Workers l'accepte au milieu (son exemple est `/*.jpg`). Un fichier écrit pour un hôte
doit rester vrai sur l'autre. On nomme les fichiers.

**Effet** : à la prochaine publication, la deuxième visite ne retélécharge plus ni les polices ni les
photos. Rien ne s'appliquera **avant** ce redéploiement (voir §5).

## 4 · Si King veut quand même une Cache Rule — la voici, exacte

À ne créer **que** si le site repasse un jour sur Pages ou sur une origine derrière la zone (cas où la
zone reprend la main sur le cache). Valeurs pour ce site :

**Chemin dans le tableau de bord**

1. <https://dash.cloudflare.com> → choisir la zone **`dmoptiquesarl.com`**.
2. Menu de gauche → **Cache** → **Cache Rules**.
3. **Create rule**.
4. **Rule name** : `DM — images et polices, 30 j au bord`.
5. **When incoming requests match** → **Custom filter expression** → coller l'expression ci-dessous
   (bouton *Edit expression*, pas le constructeur).
6. **Then** :
   - **Cache eligibility** : **Eligible for cache**
   - **Edge TTL** : **Ignore cache-control header and use this TTL** → `2592000` (30 jours)
   - **Browser TTL** : **Override origin** → `604800` (7 jours)
7. **Deploy**. Puis *Purge cache → Purge everything* une fois, sinon les anciennes réponses
   `max-age=0` restent servies.

**Expression (à coller telle quelle)**

```
(http.host eq "dmoptiquesarl.com" and http.request.uri.path.extension in {"webp" "png" "jpg" "jpeg" "ico" "woff2" "woff"})
```

**Pourquoi ces deux TTL, et pas un seul**

- **Edge 30 j** : c'est un cache à nous, purgeable en secondes. On peut être généreux.
- **Navigateur 7 j** : c'est un cache chez le patient, qu'on **ne peut pas purger**. 7 jours suffisent
  pour supprimer le coût répété, sans figer une photo qu'on remplacerait.
- Jamais de `immutable` dans une Cache Rule tant que les noms de fichiers ne sont pas hachés : une
  monture retirée du catalogue resterait affichée un an chez ceux qui l'ont vue.

**Ce que cette règle ne doit pas toucher** : le HTML. Pas de règle `Cache Everything` sur `/*` — elle
mettrait en cache la page d'accueil et King ne verrait plus ses corrections (le symptôme exact du
23/10).

## 5 · Vérifier, sur la machine de King (2 commandes)

```bash
curl -sI https://dmoptiquesarl.com/dm-logo.webp | grep -iE 'cache-control|cf-cache-status|age'
curl -sI https://dmoptiquesarl.com/ | grep -iE 'cache-control|cf-cache-status'
```

Attendu après redéploiement : `cache-control: public, max-age=31536000, immutable` sur le logo,
`cache-control: public, max-age=0, must-revalidate` sur la page d'accueil. Si la première ligne affiche
encore `max-age=0`, c'est que **le déploiement n'a pas eu lieu** — pas que la règle est mauvaise.

Et la porte technique, qui dit si tout le reste tient :

```bash
python3 tools/qa/audit_delivery.py hosting/previews/dmoptic --base https://dmoptiquesarl.com
```

## 6 · Le point qui bloque tout : la branche publiée

Tant que ce point n'est pas réglé, **aucun** des correctifs du 23/10 (menu mobile, icônes d'onglet,
cache, `og:image` JPEG, `llms.txt`) n'est en ligne.

Le 22/10, Workers Builds a été configuré avec la branche de production `arena/2fffee3b-amk` — la
branche d'une conversation terminée. Depuis, le travail se fait sur des branches neuves
(`arena/29c013f1-amk` aujourd'hui). Workers Builds publie donc **une branche qui ne bouge plus** : le
build est vert, et le site ne change pas.

**Le geste (30 secondes)** : Cloudflare → Workers & Pages → **dmoptiquesarl** → **Settings** → section
**Build** → champ **Branch** : remplacer `arena/2fffee3b-amk` par la branche en cours, ou mieux, par
`main` si le travail y est fusionné. Puis **Deploy** pour forcer une publication.

La solution durable reste le workflow `.github/workflows/deploy-dmoptic.yml` avec
`branches: ['arena/**']` (décrit dans `DEPLOIEMENT-CLOUDFLARE-2026-10-22.md` §4) : plus jamais de nom
de branche à corriger. Ce fichier n'existe pas encore dans le dépôt — il attend l'accord de King.
