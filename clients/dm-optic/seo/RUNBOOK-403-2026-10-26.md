## Geste 1 · Éteindre la duplication `http` (1 minute) — **le seul correctif technique restant**

Cloudflare → zone **dmoptiquesarl.com** → **SSL/TLS → Edge Certificates** → **Always Use HTTPS :
ON**.

- Pourquoi c'est nécessaire : aujourd'hui `http://dmoptiquesarl.com/` sert la page en 200 au lieu de
  rediriger. Deux adresses pour une page = Google en choisit une et ignore l'autre — et c'est la
  famille n°1 des 8 URL refusées.
- Comment vérifier : rouvrir `http://dmoptiquesarl.com/` dans le navigateur. L'adresse doit devenir
  `https://dmoptiquesarl.com/` **avant** l'affichage de la page.

## Geste 2 · Valider le correctif dans Search Console (1 minute)

Le 403 date du 20/10 et le site est publié depuis le 22/10 : Google n'a simplement pas retenté.

1. Search Console → propriété **`dmoptiquesarl.com`** → **Indexation → Pages**.
2. Cliquer sur **« Blocked due to access forbidden (403) »** → bouton **VALIDER LE CORRECTIF**.
3. Refaire de même pour **« Redirect error »** — la redirection `www` fonctionne depuis le 22/10.

Google repasse dans les jours qui suivent. Rien d'autre à faire : **on ne renvoie pas les URL une par
une**, ce serait 8 gestes pour un résultat identique.

## Geste 3 · Suivre la bonne propriété (2 minutes)

Les e-mails arrivent pour `https://www.dmoptiquesarl.com/`, alors que le site canonise l'apex. Une
propriété « préfixe d'URL `www` » ne peut, par construction, pas indexer des URL qui redirigent vers
l'apex : elle produira un « Redirect error » éternel.

1. Search Console → **Ajouter une propriété** → **Domaine** → `dmoptiquesarl.com` (vérification DNS,
   automatique si le domaine est chez Cloudflare).
2. Y soumettre **`https://dmoptiquesarl.com/sitemap.xml`** — il contient **16 URL** depuis le 26/10.
3. Garder l'ancienne propriété `www` **uniquement** pour valider le correctif du geste 2.

## Annexe · Si un 403 réapparaît (ne pas refaire ces cinq contrôles « au cas où »)

Ils ont été faits le 26/10 et **n'ont rien trouvé** — le pare-feu ne touchait pas Googlebot. On ne les
rouvre que si un 403 **nouveau** apparaît après le 26/10 :

1. **Security → Events**, filtre `Googlebot` + `Action = Block` sur 7 jours. C'est le seul écran qui
   tranche : s'il n'y a pas de ligne, le blocage ne vient pas de Cloudflare.
2. **Security → Bots** : Bot Fight Mode / Super Bot Fight Mode — vérifier que les *verified bots* ne
   sont pas en *Block*.
3. **Security → WAF → Custom rules** et **Rate limiting rules** : une règle par chemin ou par seuil.
4. **Zero Trust → Access → Applications** : une application (mot de passe de test) renvoie 403 à tout
   le monde, Googlebot compris.
5. **Rules → Redirect Rules** : une cible qui réinjecte `www` crée une boucle.

**Ce qu'il ne faut pas faire** : désactiver la sécurité en bloc, vider le cache, ou ajouter une règle
« Skip » pour tous les bots. Les 35 événements des dernières 24 h sont des scans `wp-config.php` et
une tentative d'exploit React (CVE-2025-55182) : la protection qui les bloque est utile au client.
